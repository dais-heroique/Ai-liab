CONFORVA API

Put a decision before execution.

Conforva lets your application send an agent action to a control boundary before the action is executed. The API authenticates with an organization API key and returns a decision, risk context, policy result and security-model result.

Base path: /api/v1   API keys are created from your Conforva account.

Quick startAuthenticationEvaluate an actionResponseAPI keysUsageErrorsSecurity model

Quick start

1. Create an account. 2. Create an agent in the dashboard. 3. Create an API key. 4. Store the key server-side. 5. Call the evaluation endpoint immediately before your own tool or business action executes.

curl -X POST https://conforva.com/api/v1/actions/evaluate \ -H "Authorization: Bearer YOUR_API_KEY" \ -H "Content-Type: application/json" \ -d '{ "agent_id": "finance-prod", "action_type": "transfer", "amount": 2000, "parameters": {"currency": "EUR"}, "description": "Transfer requested by the finance agent" }'

The returned decision is the value your application should enforce before executing the action.

Authentication

Customer API calls use an API key in the standard Bearer header. API keys are organization-scoped and must never be exposed in browser code, mobile apps or public repositories.

Authorization: Bearer cv_live_...

Keep the key in a server-side secret manager or environment variable. Revoked or unknown keys return 401.

Evaluate an action

POST/api/v1/actions/evaluate
{ "agent_id": "finance-prod", "action_type": "transfer", "amount": 2000, "parameters": { "currency": "EUR" }, "description": "Transfer requested by the finance agent" }

Request fields

FieldRequiredTypeDescription
agent_idYesstringThe agent configured in the same Conforva organization.
action_typeYesstringAction category used by risk and policy evaluation.
amountNonumber|nullOptional numeric amount used by risk and policy rules.
parametersNoobject|nullAction parameters evaluated by the configured controls.
descriptionNostringHuman-readable context supplied to the security model.

Processing order

  1. Authenticate the API key and resolve its organization.
  2. Load the organization agent and active policy rules.
  3. Compute the action risk score and risk factors.
  4. Apply deterministic policy controls.
  5. If a deterministic control blocks the action, the security model is not run.
  6. Otherwise, the security model reviews the proposed action for security and operational risks.
  7. Persist the decision and usage event for the organization.

Response

The endpoint returns JSON. Current decisions are approved or blocked. Do not treat the LLM as the final authority: deterministic policy controls remain authoritative.

{ "decision": "approved", "reason": "Action passed deterministic controls.", "policy_triggered": null, "risk_score": 18, "risk_breakdown": {"financial": 20,"security": 10}, "factors": ["transfer"], "security": { "model": "poolside/laguna-s-2.1-free", "verdict": "SAFE", "analysis": "..." }, "agent_model": "minimax/minimax-m3-free" }

When a deterministic policy blocks an action, security.verdict is NOT_RUN and the response explains that the action was stopped before security-model evaluation.

API keys

API keys are managed from the authenticated Conforva account and are scoped to its organization.

GET/v1/api-keys
POST/v1/api-keys
DELETE/v1/api-keys/:id

These management endpoints use the authenticated Conforva session rather than the customer API key. A newly created key is returned once for secure storage; use the dashboard to manage or revoke keys.

Usage

API evaluation usage is tracked per organization. Your plan includes a monthly API allowance. When the included allowance is exhausted, API evaluation is stopped until the next billing period; there is no API credit purchase flow.

GET/v1/usage

Security model

The current security model is poolside/laguna-s-2.1-free. The primary agent model is minimax/minimax-m3-free. Model output is advisory within action evaluation; deterministic controls remain the authoritative policy boundary.

For the separate agent-answer flow, Conforva also supports a two-model understanding check: the primary model produces a neutral reformulation of the request, and the independent model returns YES or NO on whether that reformulation faithfully represents the original request. A NO result is a failed understanding check.
